The stack is built and running; you are **not** starting from scratch. Your job is to fill in the missing MVP features without breaking existing conventions.

11. `/artifacts/mobile/app/onboarding.tsx` and `/artifacts/mobile/app/filters.tsx` — UI style references

### Hard conventions — do not violate these

- **Database**: Drizzle ORM, PostgreSQL. Every new table goes in `lib/db/src/schema/<name>.ts` AND is re-exported from `lib/db/src/schema/index.ts`. Primary keys are `text("id").primaryKey()` populated by `randomUUID()` from `node:crypto`. Foreign keys to users use `.references(() => usersTable.id, { onDelete: "cascade" })`.
- **Migrations**: After every schema change, run `pnpm --filter @workspace/db run generate` to produce a migration in `lib/db/migrations/`, then `pnpm --filter @workspace/db run push` to apply it in dev. Do NOT hand-write SQL migration files.
- **API routes**: One Express router per concern under `artifacts/api-server/src/routes/<name>.ts`. Mount it in `routes/index.ts`. Every route uses `requireAuth` unless explicitly public (auth + health only). Every JSON response goes through `sendValidated(res, SomeZodSchema, payload)`.
- **Zod contracts**: New request/response shapes go in `lib/api-zod/src/schemas.ts` (or a new file re-exported from `lib/api-zod/src/index.ts`). Use **Zod v4** (`import { z } from "zod/v4"`).
- **Mobile state**: All new server interactions add an `apiFetch` wrapper in `artifacts/mobile/context/AppContext.tsx`, exposed through the `useApp()` hook. Do not call `apiFetch` directly from screens.
- **Theming**: Use the `useColors()` hook from `@/hooks/useColors` for every color. Never hard-code hex values in screens. If a prototype color isn't yet in the palette (e.g. emerald-100/700 for verified, amber-100/700 for sublets), add it to the palette in one place.
- **Logging**: In route handlers use `req.log.info/warn/error(...)`. Elsewhere import `logger` from `../lib/logger`. **Never `console.log` in server code.**
- **Ports**: Always read `process.env.PORT`. Never hard-code `8080`.
- **Images**: Static `require()` for bundled assets must be a literal string. Dynamic photo URLs use `<Image source={{ uri }} />` from `expo-image`.
- **Auth header**: Mobile sends `Authorization: Bearer <token>` (handled by `utils/api.ts`). The userId is read from `req.userId` via `requireAuth` — never trust a client-supplied user ID.
- **Canonical match pair ordering**: `user1Id` is always the lexicographically smaller of the two IDs.

### What you must NOT do

- Do not rewrite the auth flow. Email/password + JWT + refresh-token rotation already works.
- Do not change the swipe / match algorithm core. You will **extend** `computeMatchScore` to use new fields.
- Do not introduce a new ORM, state library, or styling system.
- Do not add a native module that isn't supported by Expo Go.
- Do not delete the existing `forming_group` listing type from the schema. It stays in the DB but is **hidden from the new Open Rooms tab** by default (see Phase 4).

## 3. Phase 1 — Student verification

### Goal

A user signs up with any email. Until they verify a `.edu` email with a 6-digit code, they are flagged `pendingVerification` and cannot enter Match, Open Rooms, or Messages. After verification, `isVerified = true`, a "Verified @{domain}" badge appears everywhere on their profile, and they unlock the app.

### 3.1 Schema changes

Edit `lib/db/src/schema/users.ts`:

- Add `eduEmail: text("edu_email")` — nullable. The verified `.edu` address (distinct from login email so users can verify a student email separately).
- Add `eduDomain: text("edu_domain")` — nullable. Cached lowercased domain (e.g. `"northeastern.edu"`). **This is the field the verified pill renders as `Verified @{eduDomain}`.**
- Add `verifiedAt: timestamp("verified_at")` — nullable.
- Keep `isVerified` boolean.

Create `lib/db/src/schema/email_verifications.ts`:

```ts
import { pgTable, text, timestamp, integer, index } from "drizzle-orm/pg-core";
import { usersTable } from "./users";

export const emailVerificationsTable = pgTable(
  "email_verifications",
  {
    id: text("id").primaryKey(),
    userId: text("user_id").notNull().references(() => usersTable.id, { onDelete: "cascade" }),
    eduEmail: text("edu_email").notNull(),
    codeHash: text("code_hash").notNull(),         // bcrypt hash of 6-digit code
    attempts: integer("attempts").notNull().default(0),
    expiresAt: timestamp("expires_at").notNull(),
    consumedAt: timestamp("consumed_at"),
    createdAt: timestamp("created_at").notNull().defaultNow(),
  },
  (t) => [index("email_verifications_user_idx").on(t.userId)],
);

export type EmailVerification = typeof emailVerificationsTable.$inferSelect;
```

Re-export from `lib/db/src/schema/index.ts`.

### 3.2 Allowed-domain helper

Create `artifacts/api-server/src/utils/eduDomain.ts`:

```ts
export function isEduDomain(email: string): boolean {
  const domain = email.toLowerCase().split("@")[1] ?? "";
  if (domain.endsWith(".edu")) return true;
  const extra = (process.env.EDU_DOMAIN_ALLOWLIST ?? "")
    .split(",").map(s => s.trim().toLowerCase()).filter(Boolean);
  return extra.includes(domain);
}
export function extractDomain(email: string): string {
  return (email.toLowerCase().split("@")[1] ?? "").trim();
}
```

### 3.3 API routes

Create `artifacts/api-server/src/routes/verification.ts`:

- `POST /api/verification/request` — body `{ eduEmail }`. Requires auth. Validates `.edu`, generates 6-digit numeric code, bcrypt-hashes it, inserts with `expiresAt = now + 10min`, invalidates prior pending rows for this user. For dev, log code via `req.log.info({ code }, "edu verification code")`. Email sender behind env (`EMAIL_PROVIDER=resend|sendgrid|console`; `console` is default and prints to logs only). Response: `{ sent: true }`.
- `POST /api/verification/confirm` — body `{ code }`. Looks up the latest non-consumed, non-expired row for `req.userId`. Increments `attempts`; rejects after 5. On match: marks `consumedAt`, sets `users.isVerified = true`, `eduEmail`, `eduDomain`, `verifiedAt`, appends `"verified_student"` to `users.badges`. Response: `{ verified: true }`.
- `POST /api/verification/resend` — debounced (max 1/min per user). Reuses last `eduEmail`.
- `GET /api/verification/status` — returns `VerificationStatusSchema`.

Mount in `routes/index.ts`.

Add Zod schemas in `lib/api-zod/src/schemas.ts`:

```ts
export const RequestVerificationSchema = z.object({ eduEmail: z.email() });
export const ConfirmVerificationSchema = z.object({ code: z.string().regex(/^\d{6}$/) });
export const VerificationStatusSchema = z.object({
  isVerified: z.boolean(),
  eduEmail: z.string().nullable(),
  eduDomain: z.string().nullable(),
  pendingRequest: z.boolean(),
});
```

```ts
import { db, userBlocksTable } from "@workspace/db";
import { eq, or } from "drizzle-orm";
export async function getBlockedUserIds(userId: string): Promise<Set<string>> {
  const rows = await db.select().from(userBlocksTable)
    .where(or(eq(userBlocksTable.blockerId, userId), eq(userBlocksTable.blockedId, userId)));
  const ids = new Set<string>();
  for (const r of rows) ids.add(r.blockerId === userId ? r.blockedId : r.blockerId);
  return ids;
}
```

- `GET /matches` — filter out matches with blocked counterparties.

- `POST /messages/:matchId` — 403 if other party is blocked.

## 12. Tone & quality expectations

- Style-match the existing code. Route handlers use arrow functions; routers are exported by default with `IRouter` typing.
- Reuse `Badge`, `ProfileCard`, `HousingCard`, `ConversationItem`, the chip/section pattern in `filters.tsx`, and `useColors()` everywhere. Do not introduce a competing component library.
- Match the **prototype's microcopy verbatim** for the strings called out in §1.12 — no paraphrasing of "Direct messages only for MVP", "Unmatched profiles will not reappear in the feed", "Generated from onboarding answers, editable by the user", "More info = better matches, but optional fields stay lightweight", "Beta access · Student only", "Verified @{domain}", "Why you match", "Current roommate members", "Simplified MVP housing mode for open rooms and sublets".
- Error responses: always `{ error: "snake_case_code", details?: ... }`. Stick to existing codes (`verification_required`, `unauthorized`, `not_found`); create new codes sparingly.
- Loading states: every new screen with a server call shows a spinner or skeleton, never a blank screen.
- Pino logging: never log the verification code in production. Gate with `if (process.env.NODE_ENV !== "production")`.
